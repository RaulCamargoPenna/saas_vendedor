# SaaS Vendedor structured producer — draft, not activated

Contract: VPS Control ADR 0003 (`host_agent/structured_events.py`). This branch does **not** change the host collector, its bindings, the production checkout, or the deployed Compose stack. No Docker stdout/stderr is read or emitted as events. Uninstrumented deployments remain absent from the VPS Control event panel.

The image healthcheck runs `python manage.py publish_ready_event`: local HTTP GET to `/saas/` (fixed Host, 3-second timeout, no redirects) and database `SELECT 1` must both succeed. Only then, if `SAAS_EVENT_SOURCE_DIR` is explicitly set, it publishes a single version-1 `app.ready` JSONL event with integer UTC timestamp. Without opt-in it remains a readiness probe and writes no events. A failing probe or publication fails the healthcheck without printing exception details. This is **not** a statement that the public reverse proxy, all external dependencies, or the release bookkeeping succeeded. The new image uses UID/GID 10001:10001, with `/app/staticfiles` writable for collectstatic; validate deployment compatibility before merge.

The producer uses a fixed code (no request-supplied event payload), absolute no-symlink directory walk, exact 0700 directory and 0600 regular one-link file owned by its own UID/GID, a directory flock across inspection and publication, fresh closed previous-event validation, one ASCII JSONL line, 8192-byte file / 256-byte line reader-compatible bounds, private unique temporary, file fsync, exact nanosecond mtime verification, atomic replace, directory fsync, and rejects older/equal capture times. Failed directory fsync after replace may leave the new file visible; clock rollback blocks publication until time catches up. This does **not** authenticate a producer by metadata alone.

`job.succeeded` is deliberately rejected: the tracked checkout has no durable job-completion integration and the production-only untracked deploy/rollback scripts are not modified by this branch. Do not emit success merely for command invocation, health, HTTP 200, migration start, or container restart. A later separately reviewed, test-first hook may emit it only after a concrete job's durable success/bookkeeping and with no free-text, SHA, user, argument, tool output or error. Do not add a public trigger for this command.

## Release-script migration blocker (required before event opt-in)

The workflow invokes `/opt/projetos/saas_vendedor/deploy.sh`, but **neither that file nor `rollback.sh` is tracked in this repository**. On October 9, 2026, both were untracked in the production checkout. The observed deploy script resets `origin/master`, builds and starts the two-file Compose stack, then backs up and migrates the database; rollback also uses the two-file stack. Neither has a lock, pending identity gate, event overlay selection, or host-collector revocation/finalization. Because an old untracked script runs *before* the checkout changes, adding a hook only to the future commit would not protect the first deployment. Do not enable the event overlay, rotate a collector binding, merge this PR, or reboot as a substitute for migration. An untracked file survives `git reset --hard`; do not assume the Git checkout controls it.

For a separately authorized maintenance migration: (1) back up and diff both actual production scripts against reviewed, version-controlled replacements; preserve unrelated local behavior and the backup/release metadata, then make the workflow call the reviewed entrypoint rather than the untracked path. (2) Stage a durable, fsynced pending gate *before* any migration or container recreation under a per-app lock; stop/revoke the old exact-ID binding while locked. On failed revoke, abort before mutation. (3) Persist the explicit event-overlay selection so **both** deploy and rollback use the same Compose file array; never infer it from a transient shell variable or an old checkout. (4) Rebuild/recreate and wait for the *new* container ID to become healthy and publish its closed source window, then verify its actual UID/GID, mount and host directory ownership, and register only that new exact ID with the collector. (5) Start collection under the lock, verify the exact ID in agent and authenticated API, clear the pending gate with fsync and register success last. Any failed step leaves the gate in place and blocks both future deploys and rollback until manual reconciliation. A pre-release failure must not run migrations. Rehearse each failure and power-loss boundary with fake hooks and a disposable stack before switching the production workflow; a plain restart/rollback must never bypass the gate or silently lose the mount. Until this is implemented, **the safe fail-closed transition is no event activation**.

## Operator gates before activation (not performed here)

1. Review image non-root UID/GID compatibility, staticfiles ownership, current deploy/rollback behavior and healthcheck timing in a disposable staging stack with an isolated DB. On October 9, 2026, the running SaaS web process was UID/GID 0:0 and the DB process was 999:999 with identity uid_map; UID/GID 10001 were absent from passwd/group and the host process list at inspection time. This is a point-in-time check, **not** reservation: recheck all processes (including container PIDs), passwd/group and uid/gid maps immediately before provisioning, then confirm only this producer owns the host-mapped identity. Test migrations/collectstatic and external readiness after the image change. The production Compose override now declares `restart: unless-stopped` for both web and db; confirm the effective rendered config and running Docker policies after a separately authorized release, and do not reboot before verifying them.
2. Provision a **dedicated** producer host directory and bind mount for SaaS Vendedor, owned by the host-mapped UID/GID of container UID/GID 10001:10001, mode 0700, with no other app/collector writer and no alias to another source. Verify actual UID mapping, non-root runtime, mount topology, exact nano-mtime behavior and denies for a different app UID. The collector must have explicitly reviewed read access independent of any web app; never give the app a Docker socket or host collector config. A directory owned by container root or shared with another application is **not** acceptable.
3. `compose.events.yml` is an explicit leaf overlay: it is never in the ordinary two-file production command, requires `SAAS_EVENT_HOST_DIR`, mounts only the pre-existing host directory at `/run/saas-vendedor/events` with `create_host_path: false`, and sets `SAAS_EVENT_SOURCE_DIR` for the producer. It does not change the app network, image staticfiles, or DB volume. **Do not pass this overlay to any deployment yet.** Merely running `docker compose -f compose.yml -f compose.prod.yml -f compose.events.yml up -d` would bind an unregistered writer that the next deploy/rollback would drop.
4. Configure the host-only collector source binding to the exact current `(project, name, 64-hex container_id)` from a fresh private inventory snapshot; verify directory **and event-file** identity uniqueness. Container recreation requires explicit ID rotation and release gating; recycled names cannot inherit a prior binding. Validate collector timer/snapshot and web API in staging, including stale/invalid source revocation. No HTTP input may control a source path, identity, code, timestamp or count.
5. Before merge, independent security review, synthetic malicious-source tests, cross-process writer/reader races on target filesystem, build and healthcheck in staging, and release/rollback failure rehearsal are required. This branch adds pull-request tests and a permanently skipped deploy job (`&& false`) even after successful master CI, because the untracked production scripts cannot safely activate events; a separately reviewed release migration must remove that guard. **Keep this PR draft** until gates pass and maintenance is authorized. No production action was taken.
